Academic Structure

The school hierarchy must be modeled explicitly and support multi-tenancy from day one.

Hierarchy

School
 └── Academic Year
      └── Grade
           └── Class / Section
                └── Subject
                     └── Teacher
                          └── Students

Example

School: Cairo International School
Academic Year: 2026/2027

Grade: Grade 10
Section: 10A

Subjects:
  Mathematics
  Physics
  English
  Biology
  Computer Science

Multi-Tenancy

The system should support multiple schools in the future. Design all school-owned entities around a schoolId.

  • First release may contain only one school
  • Backend must enforce tenant isolation — a user from School A must never access School B data
  • Do not rely on frontend filtering for security

Configurable Elements

  • Academic years (e.g. 2026/2027, 2027/2028)
  • Grades (e.g. Grade 7–12)
  • Classes/sections (e.g. 7A, 7B, 10A)
  • Subjects — do not hardcode subject lists
  • Grading schemes (percentage, letter grade, GPA, IB-style, custom)

In Scope

  • CRUD for academic years, grades, classes, subjects
  • Student enrollments in classes
  • Teacher assignments to subjects/classes
  • All relationships persist to PostgreSQL

Out of Scope (Initial)

  • Multi-school admin UI (architecture-ready, not required in v1)
  • Curriculum-specific logic hardcoded into core

Acceptance Criteria

  • Admin can create academic year → grade → class → subject hierarchy
  • Students can be assigned to classes
  • Teachers can be assigned to subjects/classes
  • All entities are scoped by schoolId
  • Subject lists are configurable, not hardcoded
