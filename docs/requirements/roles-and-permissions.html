Roles & Permissions

Centralized RBAC — no hardcoded role checks scattered throughout the application.

Initial Roles

RoleSummary
STUDENTView dashboard, classes, lessons, submit assignments, take quizzes, view grades, attendance, announcements
TEACHERManage classes, create content, grade submissions, record attendance, publish announcements
ADMINManage one school tenant — users, academic structure, assignments, analytics, school settings. Uses apps/web admin portal.
SYSTEM_ADMINNabta platform operator — onboard schools, monitor health, manage platform ops. Uses apps/system-admin. Does not access school academic features (classes, grades, assignments).

ADMIN vs SYSTEM_ADMIN

DimensionADMIN (school)SYSTEM_ADMIN (platform)
ScopeSingle school (schoolId)All schools / platform
Clientapps/web — admin routesapps/system-admin
ManagesStudents, teachers, classes, subjects, school settingsSchool tenants, platform health, operator workflows
Does not manageOther schools, platform infraSchool academic content or day-to-day teaching

Permission Model

Permissions should eventually support granular actions:

students.read
students.write
assignments.create
assignments.grade
grades.read
grades.write
attendance.read
attendance.write

Authorization Rules

  • Create reusable NestJS guards/decorators
  • Frontend permissions control UI visibility
  • Backend permissions enforce actual authorization
  • Never rely on frontend authorization alone
  • Never trust client-provided schoolId, userId, role, or permissions
  • Derive authorization context from the authenticated user

Future Roles (Architecture-Ready)

Do not implement initially, but design for extensibility:

  • Parent
  • Principal / Vice Principal
  • Academic Coordinator
  • Department Head
  • Counselor
  • Librarian
  • School Administrator

Acceptance Criteria

  • Three school roles (STUDENT, TEACHER, ADMIN) are implemented in Phase 1
  • SYSTEM_ADMIN role and guards implemented in Phase 1c; operator console (overview, schools, health) shipped in Phase 6
  • Backend guards enforce authorization on every protected endpoint
  • Frontend hides UI elements the user cannot access
  • No hardcoded role checks in business logic — use centralized RBAC
  • Adding a new role does not require rewriting existing modules
