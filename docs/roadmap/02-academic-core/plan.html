Track A — Academic Core

Domain rules: Academic Structure. Hierarchy: School → Academic Year → Grade → Class/Section → Subject.

Slice 1 — School tenant

Goal: every academic entity is scoped by schoolId; isolation is enforced on the server.

Models: extend School if needed (slug, default locale). All new models in later slices must include schoolId, UUID id, createdAt, updatedAt.

Modules: tenant guard or interceptor on academic modules — derive schoolId from JWT for ADMIN / TEACHER / STUDENT. Never trust schoolId from request body or params. SYSTEM_ADMIN may operate across tenants (platform APIs only; not required for school academic CRUD in this phase).

Key endpoints: none new required if existing school row is enough; the guard must wrap slices 2–3.

Verify: a user from school A cannot read or write school B entities.

Slice 2 — Hierarchy APIs

Models: AcademicYear, Grade, Class (section), Subject — all with schoolId.

Relationships: School → Year → Grade → Class. Subject scoped to school (optionally linked to grade). Do not add Lesson, Assignment, or Assessment models.

Modules: NestJS modules under apps/api/src/modules/ — e.g. academic-years, grades, classes, subjects. DTOs in packages/validation; types in packages/types.

Key endpoints (ADMIN):

POST/GET    /api/v1/academic-years
GET/PATCH/DELETE /api/v1/academic-years/:id
POST/GET    /api/v1/grades
GET/PATCH/DELETE /api/v1/grades/:id
POST/GET    /api/v1/classes
GET/PATCH/DELETE /api/v1/classes/:id
POST/GET    /api/v1/subjects
GET/PATCH/DELETE /api/v1/subjects/:id

Follow list/single/error shapes in API Design. Pagination: ?page=&limit=.

Verify: an admin can create the full year → grade → class → subject chain via API.

Slice 3 — People + assignments

Models: Student and Teacher profiles (1:1 with User); Enrollment (student ↔ class); TeachingAssignment (teacher ↔ subject/class).

Modules: students, teachers (or nested routes under classes/subjects). Link profiles to existing seeded users.

Key endpoints:

POST/GET    /api/v1/students
GET/PATCH   /api/v1/students/:id
POST        /api/v1/classes/:id/enrollments
GET         /api/v1/classes/:id/enrollments
POST/GET    /api/v1/teachers
GET/PATCH   /api/v1/teachers/:id
POST        /api/v1/teaching-assignments
GET         /api/v1/classes/:id/teaching-assignments

Verify: enrollments and teaching assignments persist to PostgreSQL; list endpoints respect tenant isolation.

Slice 4 — Configurable subjects

No hardcoded subject enums in application code. Subjects are database rows. Seed may insert defaults (Mathematics, Physics, English, Biology, Computer Science) but create/update must work without a code change.

Verify: a new subject created via API appears in listings.

Slice 5 — Demo seed

Extend packages/database/prisma/seed.ts:

  • Rename or replace demo school to Egyptian International School
  • Academic year 2026/2027
  • Grades 7–12 with sample sections (e.g. 10A, 10B)
  • Subjects per grade; enroll the seeded student; assign the seeded teacher

Verify: pnpm db:seed produces a queryable demo hierarchy.

Track B — Marketing polish (Namya Khan anatomy)

Messaging source: What is Nabta? and existing marketing.* keys in packages/i18n/locales/{en,ar}.json. Design: HeroUI v3 + Nabta tokens; display type for hero per Typography.

Current home is hero + three role cards. Rebuild as a one-page landing in this section order. Navbar items (Features, For schools, Pricing) scroll to sections; sticky CTA and demo buttons scroll to #contact (the form). Old routes /features, /for-schools, /pricing, /contact redirect to those hashes.

Slice 6 — Marketing home

Components: apps/marketing/src/components/sections/ — HeroSection, BenefitsSection, HowItWorksSection, TestimonialsSection, PricingSection, FaqSection, ContactSection, MarketingFooter.

Compose in HomePage.tsx in Namya order. Navbar stays in SiteLayout.tsx (sticky hash links). Footer uses the same hashes.

i18n: keys under marketing.home.*, plus section copy from marketing.features, marketing.forSchools, marketing.pricing, marketing.contact in EN and AR. RTL-safe layout.

Contact form: on-page at #contact, POST /api/v1/marketing/contact (Resend). Closes Phase 1b Remaining #2 (form backend). Public endpoint; rate-limit; do not require JWT.

POST /api/v1/marketing/contact
Body: { name, email, message }
Response: { data: { ok: true } }

Out of scope for this slice: production deploy (stays Phase 1b Remaining), blog/CMS, real customer logos or product video.

Verify:

  • Home renders Namya sections in order on mobile and desktop
  • Navbar items scroll to #features, #for-schools, #pricing; sticky CTA to #contact
  • EN/AR + RTL for every new string
  • Light and dark themes on all sections
  • Old paths redirect to the matching hash
  • Contact form submits to the API and shows success

Out of scope (both tracks)

  • Student / teacher / admin portal UIs (Phase 3 / 4 / 6)
  • Assignments, assessments, attendance (Phase 5)
  • Notifications (Phase 7)
  • Marketing production deploy (Phase 1b Remaining)
